# 给需求提出者：怎样让 agent 修改项目

[English](REQUESTS.en.md) | 简体中文

你负责说明想解决的问题和认可结果的条件；agent 负责阅读仓库、定位模块、实现、测试并解释证据。不必知道函数名，不必先设计协议，也不需要购买某一种 agent 服务。

先把仓库放到你的开发环境中，让 agent 能够读取源码。若它只能聊天，下面的模板仍可用于整理 Issue，但聊天中的方案不代表代码已经修改或测试。

## 一份有效需求的七个部分

| 内容 | 应写什么 | 示例 |
|---|---|---|
| 场景 | 在什么模式、设备和操作下使用 | 桌面模式，双手控制器，拖动窗口 |
| 当前行为 | 现在实际发生什么 | 另一只手点击时，正在拖动的目标发生跳动 |
| 期望行为 | 修改后应该观察到什么 | 拖动保持在最初捕获的手和面板，释放后才允许新的操作 |
| 范围 | 哪些行为在本次目标内 | 只修复双手输入仲裁，不增加新快捷键 |
| 边界 | 取消、断连、追踪失效、重启怎么处理 | 失去焦点后释放已按下的键，重连不补发旧点击 |
| 验收 | 用什么操作判断成功 | 同一复现步骤重复 10 次，目标不跳动且无卡住按键 |
| 环境与授权 | 版本、工具、设备以及允许的动作 | 允许本地构建/离线测试，实机由我操作 |

示例是需求写法，不是对现有缺陷或新功能的断言。数字阈值由实际需求决定；无法确定时要求 agent 提出测量方案，不能让它凭空宣称达到指标。

## 完整需求模板

复制后填写；不清楚的项写“请先调查”，不要编造环境或测试结果。

```text
标题：
目标用户/使用场景：
当前行为（或要解决的困难）：
期望行为：
操作入口/显示位置：
默认值、范围、是否保存：
失效、取消、重启、断连时的行为：
兼容要求（旧设置/旧设备/旧版本）：
本次范围与明确不做的事：

环境：
- 源码提交/发行版本：
- PC 系统、GPU/驱动：
- Frame 系统/运行时（没有头显就说明）：
- 桌面或 VR、连接方式、编码/分辨率/FPS 等相关设置：
- 可用构建环境/SDK：

验收：
1. 在……条件下，执行……，应观察到……。
2. 当……异常发生时，应……。
3. 原有……行为仍应……。

允许的操作：本地修改/构建/离线测试；其他操作列明。
部署、服务变更、网络设备和发布限制：
证据：脱敏复现步骤、短日志、必要截图；没有就写无。
```

同一需求不要塞入多个不相关的愿望。例如“新增一个设置、重做 UI、替换网络协议、重写渲染”应拆成可单独验收的工作；必要的双端协议修改仍属于同一个功能。

## 提示词 A：直接实现一个明确需求

```text
请在当前 SurfXR / SurfXR 仓库实现以下需求：
【粘贴已填写的需求模板】

先阅读 AGENTS.md 和 surfxr/docs/ARCHITECTURE.md、TOOLS.md、PROTOCOL.md、
AGENT_GUIDE.md；检查工作树，保留无关改动。
先说明拥有模块、职责、受影响接口和验收计划，然后完成实现。
请按 DEVELOPMENT.md 维护相关消费者，按 TESTING.md 选择必要检查。
使用已有构建/安装/shader 工具，所有产物放在根 build/。
功能若跨 PC/Frame，双端一起修改；配置变更要覆盖旧格式迁移。
在本次授权范围内继续完成，不要只输出方案。
提交连贯且验证过的改动，报告提交 ID、测试结果、未验证项和人工验收步骤。
```

若没有写操作授权，可以补充：“本次仅本地编辑、构建和离线测试；设备部署及服务重启由我决定。”如果希望 agent 部署，应明确目标设备、安装版本、允许的服务操作和回退要求，不能只写“随便弄好”。

## 提示词 B：问题不清楚，先调查

```text
我遇到的问题是：【现象、操作、出现频率、环境】。
请先读取仓库规则和维护文档，沿实际生产路径调查。
暂不修改运行代码，不安装、不重启服务、不连接设备。
请区分已确认事实、推测和缺少的证据，指出拥有模块与可能受影响接口。
优先用现有离线检查缩小范围；给出最小修复建议和可以验证它的步骤。
如果需要我补充信息，只问会影响判断的关键问题。
```

这个模板明确要求调查，因此调查结论不是实现完成。决定方案后，再用 A 模板要求实现，保留已有调查结果。

## 提示词 C：修复一个 Bug

```text
请修复以下可复现问题：
版本/提交：【填写】
前置条件：【填写】
步骤：1. …… 2. …… 3. ……
期望：【填写】
实际：【填写】
频率：【必现/每 N 次约发生 M 次】
证据：【脱敏日志或文件位置】

读取 AGENTS.md 及架构、工具、SurfXR、Agent 指南后，定位实际责任模块。
用现有 fixture 增加能触发根因的回归检查；不要用复制实现的测试掩盖问题。
修复正常路径和相关取消/断连/退出路径，保留既有协议、配置与资源生命周期。
完成必要构建和测试，提交并说明复现前后结果；没有实机就明确列出待验收项。
授权范围：【填写】。
```

## 提示词 D：性能或画质需求

```text
希望改善：【具体瓶颈或可见问题】。
场景与固定条件：【分辨率/FPS/码率/编码、设备、驱动、连接方式、素材】。
基线：【目前观测值、统计方式、观察时长；未知则先测量】。
目标：【可测量目标与允许波动；未知则请提出合理比较方法】。
允许的代价：【画质、CPU/GPU、内存、功耗等约束】。
禁止扩大范围：【例如只修正颜色解释，不改变空间滤波算法】。

先核对指标在现有 telemetry 中的定义，再定位瓶颈。
复用现有计时、编码/解码和 GPU 测试工具，不新增平行采集器。
相同条件比较修改前后，保留队列上界和 GPU/decoder 生命周期。
报告样本时长、统计方式、环境与局限；没有测量证据不要写“更快/更清晰”。
遵守仓库 Agent 指南，完成实现和验证后提交。
授权范围：【填写】。
```

## 提示词 E：审查并准备人工验收

```text
请审查提交/分支：【填写】是否满足这份需求：【粘贴需求】。
本次先不修改代码，也不部署。读取仓库规则和相关合约，检查 diff 与已有证据。
逐条标记验收条件：已证明、仍需测试、失败或不适用，并说明依据。
区分构建、CPU/回环、离屏 GPU、真实头显和佩戴体验。
检查是否只改了一端、是否有配置迁移/异常释放/队列上界问题。
给我可以照做的人工验收步骤：前置条件、操作、预期、失败时收集什么。
```

## 怎样写可验收条件

用“前置条件 → 操作 → 观察结果”组织，不要只写“体验正常”。以下以假设的本地 HUD 设置为例：

| 情况 | 操作 | 可观察结果 |
|---|---|---|
| 默认行为 | 在隔离测试配置中首次启动 | 显示需求指定的默认值，不冒充已接受的远端状态 |
| 正常修改 | 在 Dashboard 改值并打开串流内设置 | 两个入口显示一致，实际行为符合设置 |
| 持久化 | 正常退出并重启 | 已保存值仍然生效 |
| 边界 | 设置最小值/最大值，尝试越界值 | 保持规定范围或明确拒绝，不崩溃 |
| 失效 | 模拟模型中的无效数据；实机按约定操作 | 无效状态按需求隐藏或提示，不显示过期结果 |
| 兼容 | 用历史格式 fixture 加载 | 原有字段保留，新字段获得规定默认值 |
| 回归 | 使用原有 HUD 与相关开关 | 已约定的既有功能继续正常 |

不要删除用户配置来模拟首次运行；使用隔离 fixture 或先约定备份和恢复。测试系统状态的故障方式也应事先明确，避免为验证而破坏正在工作的设备。

## 怎样判断 agent 真正完成了

看交付的行为与证据，而不是回答长度。最少应有以下信息：

- 修改位于哪个模块，为什么在那里，是否影响另一端或保存格式。
- 哪个提交包含改动，是否保留你的其他修改。
- 实际运行的命令、平台、结果和未解决警告。
- 哪些需求已被自动检查证明，哪些还需要你执行。
- 是否安装/重启/连接过设备，当前运行版本是什么。

“编译成功”只说明构建层面；“离屏 Vulkan 测试通过”不等于头显运行时通过。历史 `VALIDATION.md` 也不能替代本次提交的结果。

## 你如何做最终验收

1. 确认要验收的提交、PC 与 Frame 版本和部署包。通过了源码测试但仍运行旧安装时，无法判断新行为。
2. 从 agent 给出的验收表逐项操作，记录预期与实际，不临时改变一堆无关设置。
3. 涉及体验时记录画面、声音、输入、舒适度和使用时长；涉及性能时固定条件并说明样本。
4. 失败时记录第一个异常、时间、步骤、模式、版本和脱敏片段，交回 agent 继续定位。
5. 明确回复“哪些项通过，哪些项未测/失败”。只写“可以了”很难判断接受的是哪一版和哪一项。

可用回复：

```text
验收提交/包：……；PC/Frame 环境：……；观察时长：……。
通过：A1、A2、A4。A3 未测，原因：……。
失败：A5；步骤：……；实际：……；期望：……；脱敏证据：……。
请继续修复 A5，保留其他已通过行为。允许的操作仍为：……。
```

日志和截图应先脱敏：删除密钥、配对材料、账户/主机标识、私人桌面内容及无关流数据。保留定位所需的错误码、相对时间、状态和计数器；不要向 agent 发送账户密码来换取更方便的复现。
