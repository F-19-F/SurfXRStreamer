# 首次公开仓库前的准备

[English](OPEN_SOURCE.en.md) | 简体中文

本文用于维护者把当前工程整理为可公开协作的项目。它记录已具备的入口和发布前需要实际完成的事项，不代表许可证审查、安全审计、全新环境构建或当前版本实机验收已经通过。

当前文档准备状态（2026-11-07，Asia/Shanghai）：

| 项目 | 当前可核实状态 | 仍需做什么 |
|---|---|---|
| 双端源码与模块职责 | PC、Frame、shared 同仓；架构和工具入口已有说明 | 在新环境按文档验证所选发布版本 |
| 贡献与 agent 入口 | README、CONTRIBUTING、Agent/需求/开发/测试指南及 Issue/PR 模板已提供 | 发布到实际平台后检查入口可访问 |
| 导入来源与声明 | 根 NOTICE、SurfXR/OpenVR 及 shader 声明存在 | 审查完整发布范围及新引入依赖 |
| 项目自身许可证 | 根 [LICENSE](../../LICENSE) 采用 GPL-3.0-only，适用于项目自有代码和文档；第三方条款保留 | 核对实际发行物附带 GPL-3.0-only 及对应第三方声明 |
| 版本验证 | VALIDATION 说明所选提交的验证要求 | 为本次发行生成新证据，不能复用旧版本结论 |
| 公开地址与支持入口 | 本文不指定未知的远程地址、人员或联系方式 | 维护者选择托管地址、问题入口和私密安全反馈渠道 |

## 1. 确定授权范围和来源

项目自有代码和文档采用根 [GNU GPL v3 (GPL-3.0-only)](../../LICENSE)。先阅读 [NOTICE.md](../../NOTICE.md)、[架构来源记录](ARCHITECTURE.md)及导入树中的声明；`pc/surfxr-server` 的 Cargo 许可字段标记当前 GPL 衍生作品，其 LICENSE 保留 ALVR 上游 MIT 声明，SurfXR、OpenVR、vendor 和 shader 的原许可继续有效。

- [x] 按权利人选择，为项目自有代码和文档添加 GPL-3.0-only LICENSE，并在 README/贡献说明中链接。
- [ ] 核对发行物中包含根 LICENSE，并逐项确认新增图片、字体及其他素材的授权范围。
- [ ] 核对导入 SurfXR、OpenVR、vendor 和 shader 的来源、版本与保留声明。
- [ ] 新依赖/复制代码的来源和许可证位置可追溯，二进制包包含其对应声明。
- [ ] 核对可选编码器、运行库和 bundled tools 在实际发行配置下的 notices。
- [ ] 处理历史 `cargo-about` 许可元数据诊断，记录实际处理结果；“打包退出成功”不等于元数据审查完成。
- [ ] 不将私有系统 SDK/sysroot、用户数据或未确认分发范围的素材加入公开仓库/发行包。

项目级 GPL-3.0-only 已由权利人选定；这不替代第三方组件和新增素材的逐项许可核对，也不授权更改它们的署名或许可条件。

## 2. 检查将要公开的内容

审查范围包括工作树、将要推送的提交历史/分支/tag、附件、构建日志和最终 ZIP/安装包，不仅是当前 `git diff`。`.gitignore` 不会移除历史上已经跟踪的内容。

- [ ] 排除凭据、配对记录、信任数据库、会话/用户设置、私有地址清单和 SDK 快照。
- [ ] 检查日志中的账户、主机标识、本机路径和原始 packet payload；公开复现材料只保留必要信息。
- [ ] 排除私人桌面截图/录屏/音频和没有公开授权的测试素材。
- [ ] 构建产物、Cargo cache、依赖下载、暂存和报告位于根 `build/`；发行物位于 `release/`，均不混入源码提交。
- [ ] 使用具备能力的扫描工具检查历史和包，并人工复核命中；单次关键字搜索不能证明“没有秘密”。

如果发现曾提交的秘密，先停止公开该内容，由维护者处理撤销/轮换和历史清理。删除当前文件并不表示历史泄露已经解决。重写历史和 force push 必须另行确认范围，不作为文档整理的附带动作。

## 3. 证明陌生人能按文档工作

在干净 checkout/worktree 与明确的环境中验证，不能依赖维护者的既有 cache 或兄弟仓库：

- [ ] [首次开发](GETTING_STARTED.md)与 [WSL 构建](WSL_BUILD.md) 中的前置条件足够，未把维护者路径当默认值。
- [ ] `scripts/Build-PC.ps1 -PrepareDependencies` 能生成完整 PC payload，相关 native/Cargo tests 另行运行并记录。
- [ ] Frame `build_viewer.py --local` 生成目标配置的报告；区分 x86_64、QEMU ARM64 和目标 SDK ARM64。
- [ ] shader 生成工具及版本有说明，`--check` 与跟踪资源一致。
- [ ] `check_structure.py` 通过，未静默扩大上游 baseline。
- [ ] 构建不安装、不配对、不启停真实服务；`-NoStart` 的部署语义已向使用者说明。
- [ ] 缺少设备的人能够执行文档/CPU/回环贡献，并清楚标出尚未覆盖的验收。

不在此文件勾选未实际运行的项；把证据写入所选提交的报告或发布记录。更改运行代码后，旧结果不自动延续。

## 4. 形成一次可追溯发行

按 [RELEASE.md](RELEASE.md) 使用已有工具打包，冻结源代码、完成验证并提交后再打包。

- [ ] PC 与 Frame 是匹配版本，记录源码提交、工具链、目标 OS/runtime 和已知限制。
- [ ] ARM64 客户端由目标 SDK 构建，manifest、SHA-256 和包内资产通过现有校验。
- [ ] 包中没有配置/密钥/私有素材；相应 notices 随包保留。
- [ ] 构建、离线、离屏 GPU、真实设备和佩戴验收分别记录；标明未测项目。
- [ ] 安装/升级/卸载和用户数据保留有证据；若未执行，明确列为限制。
- [ ] 给使用者提供安装说明、变化、兼容要求和回退方法，而不是只发一个二进制文件。

部署目标与编译输出分离；发布不会自动升级当前正在运行的安装。未经过运行验证的构建应如实标注，不使用“稳定、全硬件兼容”等无证据承诺。

## 5. 开放协作入口

- [ ] 确定实际托管地址，检查 README、文档导航和相对链接的渲染。
- [ ] 确定 Issue/PR 是否开放，模板是否可用；`.github` 模板适用于 GitHub，其他平台可复制字段。
- [ ] 指明维护范围、支持的平台和当前可提供的设备验收条件。
- [ ] 建立可用的私密安全问题反馈入口后，再发布对应联系方式；不要把未知邮箱写进 SECURITY 文件。
- [ ] 根据维护者实际承诺设置审查/合并权限与自动检查，不能把文档里的建议描述成已经启用的 CI 或分支保护。
- [ ] 让一位不了解项目的人，或一个没有历史聊天上下文的 agent，按需求模板完成一次小改动并提供可审查结果。

当前文档不声明已有 CI、专职维护团队、CLA/DCO、支持时限或漏洞响应承诺。这些政策确定后应以实际配置和文件为准更新说明。
