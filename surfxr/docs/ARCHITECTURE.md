# SurfXR architecture and ownership

## Source graph

The PC `cargo xtask` build copies the current `scripts/Install-Frame.ps1` and private `scripts/launch` release adapters to `frame-installer/` beside Dashboard; portable/Setup packaging requires and hashes these scripts. Dashboard uses that PC-owned adapter and separately defaults its ARM64 payload folder to `frame-client/`. An older selected Frame archive cannot override the Dashboard command contract. Its original manifest and payload remain unchanged. `frame_release_commands.ps1` is a private command generator used by both dry-run rendering and the existing release executor, not a second installer. Plan validates local hashes and shows SSH/SCP arguments, remote shell commands and JSON stdin, including pairing identity retrieval; it does not resolve/contact the target or mutate it. The remote staging root is explicitly unresolved until SSH preparation returns it. Windows PowerShell initializes its own module path, avoiding an inherited PowerShell 7 path. Entry startup failures are also retained in the Dashboard result.

Dashboard desktop session ownership: `dashboard/frame_desktop.rs` owns bounded admission tickets, while `frame_desktop_sessions.rs` owns their in-memory UI projections and explicit revocation sockets. `pc/desktop/dashboard.*` implements the matching native notification client; `pc/daemon/session.cpp` owns desktop/VR/idle mode and transport cancellation. Devices reads these projections alongside the independently owned SteamVR client state, including one-time paired sessions. Disconnect preserves pairing and targets only the selected ticket. Confirmed Dashboard exit revokes all sessions before SteamVR shutdown or thread joins; closing to tray does not revoke. The persistent SYSTEM service stays installed/running. [PC-local broker contracts](PROTOCOL.md) describe compatibility and unchanged crash/stall grace. No runtime-internal adaptation is involved.

双端语言选择、翻译呈现层、内嵌字体和旧品牌兼容边界见 [LOCALIZATION.md](LOCALIZATION.md)。Frame 词表和字形由 `frame/ui` 所有，Dashboard/launcher 仅在显示边界使用；PC Dashboard 维护自己的呈现词表。

`pc/surfxr-server` is the retained ALVR-derived PC Rust workspace and SteamVR C++ driver. Dashboard owns device trust, session configuration and PC user controls. `pc/daemon` owns the Windows SYSTEM service, persistent Frame admission, backend transitions and worker leases. `pc/desktop` owns desktop duplication, desktop input, audio capture, encoding and media delivery. Private GPU IPC joins these modules without transferring ownership of native handles to arbitrary consumers.

`shared/surfxr` owns bounded protocol codecs, authenticated desktop records, stream framing, FEC and SurfXR extension records. HMAC and AES-GCM are local implementations over platform crypto providers; directional keys and replay windows belong to each authenticated session. `shared/protocol` contains only internal geometry, semantic input events and typed client commands. It does not implement another network backend.

`frame/surfxr` owns the current SurfXR protocol negotiation and session lifecycle (historical wire codecs remain test fixtures). `frame/session/include/surfxr/session.hpp` is its callback/options interface. `frame/app` assembles the client, receiver worker, status and command channels. `frame/tracking` owns Stage-space state, pose identity, display-time prediction, metadata pairing and haptic mailboxes. `frame/media` owns bounded asynchronous decoders, audio and microphone resources. `frame/xr` owns runtime handles, Vulkan presentation, local UI, timewarp, foveation reconstruction and GPU fences. `frame/dashboard` and `frame/launcher/native` own configuration and launch orchestration; neither embeds a second transport implementation.

## Lifecycle and data contracts

PC boolean input updates belong to `server_openvr/BooleanInput`, resolved once per device activation. On Windows x64, SteamVR can linker-fold its public input update adapter with a server-host pose adapter. A third-party pose detour can then narrow a 64-bit input handle to a 32-bit device index. The resolver only follows the adapter's original target when bounded instruction-semantic analysis of the live creation method still proves the object layout, and a read-only non-executable mapping of the matching runtime PE proves the original boolean forwarding ABI. It neither rewrites runtime code nor guesses a private interface version or manufactures handles. Other APIs, unpatched adapters, unsupported ABIs and platforms keep the public input interface. The shared semantic analyzer derives offsets and slots from public method entrypoints, rejects side effects and argument changes, and never scans for runtime byte patterns. Frame input compiles against the same pinned public OpenVR SDK submodule as PC, rather than older sysroot sample headers. It likewise follows all four public Boolean/skeleton methods to a proven shared target and dynamically patches/restores their derived slots; it requests no private interface version. Dashboard overlay bindings and the interface identifier are generated from the public SDK. All internal adaptation emits a diagnostic and follows [RUNTIME_ADAPTATION.md](RUNTIME_ADAPTATION.md). Component registration, system/D-pad paths and wire formats are unchanged. Controller bone tables live in `ControllerBones`, `ControllerTrigger` and `ControllerTriggerClick`; the former oversized `Controller.cpp` exception is removed.

Local keyboard/mode shortcuts belong to `frame/tracking/shortcut`, with button action validity and focus owned by `frame/xr`; hand spatial pose is not a button prerequisite. Frame uses only its explicit right Menu input; generic Menu bindings and left View never select the local gesture. Both edges must settle for 30 ms, a click is 30–500 ms, and the second physical down must follow the first release within 350 ms. There is no additional post-switch/System quiet interval. System cancels both hands while held; re-arming requires observed stable release. Invalid button actions, lost focus, profile changes, backward time and sampling gaps over 100 ms discard pending clicks. Focus events reset even when loss/regain occurs between samples. Logical mode changes consume old pending/second clicks, retaining only already debounced released hands; first-image presentation changes must not cancel a newer gesture. Recognized keyboard commands enter `VrUiModel::toggle_keyboard` independently of pointing rays; invalid hand poses still cancel pointer capture and dragging. The diagnostic shortcut guard means neither hand is armed, not a timed lockout. Native System state continues to be observed in desktop mode without requesting capture, so a System press still cancels Menu gestures after leaving VR. Remote System/D-pad transport and the separate four-click Take Over release gesture are unchanged.

PC Steam Frame HMD icon properties belong to `server_openvr/frame_headset_props`. All nine device states name existing `{vrlink}` Frame assets: standby/off use the Frame off icon, searching uses searching, errors use error, alerts use info, and low battery uses ready_low. Generic suffix construction is retained only for other emulation modes. The former oversized `props.rs` is split into property conversion, device properties and icon owners; its imported line-limit exception is removed.

The native launcher connection controller owns atomic start/profile selection. Deployment's required `link` maps to optional IPC `start.profile`; validate the requested mode/profile before changing configuration, reject a different active profile, then select it before discovery/launch. Unspecified-profile UI/CLI starts keep the saved selection. Release installation preserves profiles/endpoints and does not imply a link change. The active interface/host, not just a launch argument, is the evidence for the actual streaming route.

Desktop controller pointer stabilization belongs to `frame/ui`; `frame/xr` draws the resulting cursor and laser endpoint. Video hover damps fine tremor with a motion-adaptive 4-35 ms time constant. After aiming within a 3 mm panel-space radius for 50 ms, an early trigger pull (0.10) can pin the displayed target for at most 250 ms and 25 mm of displacement. A digital left/right press can retain the last displayed target within 12 mm. Preparation rearms only after trigger release (0.08); it never emits a button edge. Large deliberate moves, stale samples, other UI regions, grip, source changes and input release discard hover history. These are local interaction rules, not saved preferences or protocol extensions.

Pending left clicks retain the same visible target through release. Drag recognition still starts at the actual select edge, requires at least 100 ms held, and now requires 18 mm of displacement from the raw down pose sustained for 60 ms. This prevents squeeze displacement or a one-frame tracking spike from creating an accidental drag. A real drag emits down at the stable click target, then follows the current ray on its original panel. Capture release prevents the other hand from moving or scrolling that cursor in the same frame. Existing cancellation and all-up paths remain authoritative. CPU model checks cover these rules; actual pointing comfort and threshold tuning require wearer acceptance on a headset.

On Windows, the PC Dashboard owns a notification-area icon and a hidden settings window by default. Closing the window hides it; Exit completely from the panel opens a confirmation dialog; Cancel or Escape leaves Dashboard running. Exit from the tray menu proceeds directly. Both confirmed panel exit and tray exit end Dashboard and its admission workers through the existing teardown path. SteamVR follows the existing start/stop-with-Dashboard preference only on process exit. The installed SYSTEM service retains its independent lifetime. A named per-logon instance guard redirects another launch to the existing panel before logging, session cleanup or broker ownership begins. Hidden-window event processing continues in the application logic callback. If tray creation fails, the settings window stays accessible.

The instance guard is independent of the optional tray and stays in `main` until the native Dashboard and its DataSources workers finish teardown. Window/icon creation failure keeps that guard while showing the ordinary settings window; a second process cannot become another admission owner. Failure to create the instance mutex itself aborts startup before session or worker ownership. Without a tray, closing the visible window follows the existing full-exit path.

Installation owns desktop service actions; Quick setup / Startup & diagnostics owns the independent Dashboard logon switch and the combined desktop boot option. Opting into automatic desktop startup configures the existing service for boot and registers the current Dashboard executable in the current user's Windows Run key with `--tray` for tray startup after logon. These are separate owners: the service cannot admit trusted devices until Dashboard is running. Service operations share one explicitly elevated, fixed-command worker for the Dashboard process lifetime; denied service changes do not register logon startup, and failed logon registration attempts to restore the previous service mode. Service updates preserve startup type; uninstall removes this user's Dashboard startup registration. Build commands do not change these registrations.

Dashboard's private `tray/panel.rs` owns a UI-thread startup visibility guard. eframe 0.35 unconditionally reveals the root window after its first painted frame, and winit also reapplies the visible window style; setting the initial viewport visibility alone is insufficient. Before rendering, tray startup suppresses both native show paths without first displaying or minimizing the panel. An explicit tray click or manual duplicate launch releases the guard and synchronizes winit's visibility before showing the panel. `--show-settings` bypasses the guard; duplicate `--tray` launches leave the current panel state alone. The guard is removed on panel destruction or Dashboard teardown. The isolated native eframe test checks show events (including transient flashes), duplicate startup, manual activation, close-to-tray, reopening and exit without starting streaming owners or changing startup registrations.

Desktop frame rate, bitrate per monitor and monitor count are projected into Quick setup / Picture & performance at their original session paths. The encoder preset exposes only SurfXR default and Custom: default matches the complete existing tuning bundle, while Custom preserves any differing tuning. NVIDIA Multi pass is projected into the same quick panel at its existing `video.encoder_config.nvenc.multi_pass` path, with explicit single-pass, quarter-resolution and full-resolution two-pass (quality) labels. Selecting full-resolution two-pass therefore displays Custom instead of a misleading Speed preset. Opening settings remains read-only; applying SurfXR default restores single-pass tuning. SurfXR gaze and upstream foveated encoding are exclusive Dashboard selections, including advanced switches and resets; enabling either submits the other toggle's disable in the same accepted update while retaining quality values. New sessions default to gaze only through the PC session defaults adapter. Existing saved conflicts are shown for explicit resolution, without rewriting a configuration merely because a page was opened.

Desktop pointer arbitration belongs to `pc/desktop`. The current owner persists through inactivity, releases and policy edits. The other source must move a net 12 physical desktop pixels within a continuous movement burst to request ownership; a 150 ms gap discards partial motion. Bounded back-and-forth jitter is not summed as travel. The existing simultaneous-motion policy resolves a qualifying challenge while the current owner has moved within 150 ms, defaulting to VR. Denied motion is consumed immediately, never replayed when activity expires. VR retains its two-pixel movement deadband while owning the pointer. Its first sample after a release or display change establishes a baseline and cannot take ownership from PC.

The dedicated Windows mouse-hook thread counts native motion relative to the last admitted cursor position, including suppressed relative movement. Tagged SurfXR injections update that position without becoming PC movement. While VR owns the cursor, unqualified/losing native movement is suppressed to avoid interleaved jumps. Ownership and its epoch are atomic; each input thread owns its own motion accumulator, with no hook wait on networking or settings. Rejected downs/wheel events cannot act at the other owner's cursor; previously held VR buttons always release without repositioning when PC wins. Keyboard/IME ownership in VR mode keeps its existing behavior.

The simultaneous-motion preference is PC authoritative at `frame_settings_sync.prefer_pc_mouse` (missing means false / VR priority). The existing session revision, receipts and latest accepted edit rules cover it together with video controls. The daemon reads the policy on its existing policy worker and shares an atomic snapshot through desktop-module ABI v3 (the policy callback introduced in v2 is retained); the input loop performs no settings network calls. Frame exposes it in Devices in both Dashboard and the in-stream panel. Local settings format v5 appends `DESKTOP_POINTER_PRIORITY` after the unchanged reserved slot; v1-v4 migrate to VR priority. Cached values never become unsolicited edits.

The PC authoritative video settings use accepted snapshots and serials. A successful local enqueue is not an acknowledgement. FPS and quality-tier edits are saved for explicit SteamVR restart; bitrate can update an active session. Local image quality, input capture, boundary synchronization and HUD preferences stay on Frame.

Frame's compiled first-run stream values share one initializer in `remote_settings.hpp`: VR 120 FPS, Godlike (3072 × 3264 per eye), constant 100 Mbps; desktop 60 FPS and 60 Mbps; gaze enabled and simultaneous pointer motion preferring VR. The PC session defaults test checks this initializer against actual PC defaults. Viewer/session, launcher, cached preferences and dashboard fallbacks use these values without asserting server acknowledgement. Existing saved preferences retain their values and the first accepted PC snapshot remains authoritative; local microphone mute/volume defaults are independent.

Frame Dashboard and the in-stream settings panel group controls into Stream, Image, Devices and Diagnostics. Device synchronization owns safety boundary and the battery source choice; diagnostic overlays are separate from image processing. Dashboard always shows actual battery capacity in its status card, independently of the source reported to PC. Category navigation is local UI state and retains the existing preference IDs and acceptance serials.

The optional Mini HUD belongs to `frame/ui`, with VIEW-space composition and raw local eye-gaze sampling in `frame/xr`. It is independent of the detailed timing HUD and defaults off, with FPS and upstream-to-XR-submit latency selected at the upper right. New video frame interval and receive-to-decoder-output time are additional selectable rows. These reuse `PerformanceOverlay` and `SurfxrPerformance`; latency is not a photon measurement. A fixed texture allocation is cropped to the selected rows and refreshed at 4 Hz, while gaze visibility is evaluated each rendered VR frame. Gaze-only mode uses an unclipped VIEW-space ray at the local display target, an 80 ms dwell and 250 ms leave grace; invalid or stale gaze immediately hides values. Tracked queries expire after 100 ms; reported sample times may be up to 100 ms old or predicted ahead. When the runtime reports no sample time, the active tracked query supplies freshness, so sensor age cannot be independently verified. An independent target-marker preference can leave the HUD region outlined while values are hidden. This local ray never alters SurfXR tracking or crop coordinates.

Mini HUD controls are local input preferences, appended at IDs 5-14. Format v6 appends the enable, four row selections, gaze-only, marker, horizontal/vertical position (0-100), and size (50-200 percent) fields after unchanged v5 fields. Versions 1-5 and historical product headers retain their existing values and receive the new defaults. Dashboard, in-stream diagnostics, the native launcher and viewer status/commands use the same IDs, bounds and acceptance serials. Existing reserved storage slots are unchanged.

The persistent connection owns desktop/VR mode transitions. `frame/surfxr` prepares an explicitly requested SteamVR runtime on a joined worker while the unified desktop receiver keeps running. Request serials reject late readiness after cancellation or a newer request; startup failure leaves the desktop source active. The prepared launch is consumed once by the VR session, avoiding a second launch request. XR selects live sources and desktop decode demand from actual video availability, independently of the requested mode. Old decoder images are never copied/replayed as frozen transition backgrounds. Source shutdown, decoder retirement and the next generation handshake remain sequential, so the actual source handoff can still have a video gap; this is not a concurrent dual-decoder seamless-handoff guarantee.

`frame/ui` owns the transient switching HUD and per-transition dismissal. `frame/xr` composes its small translucent lower-right VIEW-space quad near the center (0.26 m right, 0.18 m down at 1.2 m) during initial waiting, desktop/VR switching and recovery, including over a still-playing source. Completion hides it; one right Menu click dismisses only the current transition. A new target or later transition can show it again. There is no close icon or trigger hit region. Optional composition respects the runtime layer budget and only a presented HUD consumes the Menu dismissal. `TransitionHudEnabled` appends local preference ID 15 (default on); input-preferences format v7 appends `TRANSITION_HUD_ENABLED`, preserving IDs 0-14 and migrating v1-v6 with the new default. Dashboard and in-stream Diagnostics / Overlays expose Switching HUD, independently of Mini HUD; the native desktop window exposes the same persistent switch. Existing IPC acceptance serials and cached-transition telemetry fields are unchanged.

Each media configuration starts a generation. Metadata and both eyes are matched to the same remote timestamp, tracking ledger entry and Stage epoch. Reset discards stale associations. Queues are bounded; backpressure requests recovery instead of growing memory indefinitely.

The current Frame color contract is 8-bit SDR with sRGB RGB code values. PC desktop capture and the SDR VR render targets preserve those values; their encoders signal sRGB transfer and BT.709 primaries. YCbCr matrix and range are separate properties: the direct VR NVENC path signals BT.709 full range, while the desktop FFmpeg packed-RGB path signals BT.601 limited range. For V4L2 output, Frame treats each known matrix/range field from the exact picture's SPS as authoritative because the device may report a contradictory matrix. Missing SPS fields fall back to decoded-frame metadata and then the existing defaults. Raw decoder metadata remains available in diagnostics; both CPU RGBA conversion and GPU NV12 publication use the same effective values. A color tag does not configure a software RGB-to-YUV converter: the optional Windows GPL encoder explicitly sets swscale's matrix and range to match its output metadata. HDR and non-default encoding gamma remain outside the negotiated Frame contract.

PC `server_openvr` owns per-eye texture interpretation in private `FrameRenderInput`. Shared texture allocation and sampling-view formats remain as requested, including typed UNORM. The existing shader decodes sampled SDR UNORM RGB once; sRGB views already decode in hardware, and linear floating-point textures must not be decoded again. Each eye selects its own view/correction. RGB transfer functions leave alpha unchanged. No texture reinterpretation, copy texture, GPU copy, CPU readback or additional per-frame image allocation is introduced. Shared handles, queueing and source/fence lifetimes retain their existing owners. `FrameRenderStartup.cpp` owns initialization/output accessors and `FrameRender.cpp` owns per-frame composition; both are below 500 lines and the old oversized import exception is removed.

Frame rendering retains the existing sampling algorithms and shader bytes. VR samples NV12 planes, applies the selected matrix/range, then decodes the resulting RGB to linear light for the sRGB swapchain. Desktop retains its existing full-resolution NV12-to-sRGB cache. Differences between encoded-domain and linear-domain spatial filtering are outside the color-cast repair scope; they do not authorize a new filter, conversion cache or sharpening algorithm. Matrix/range interpretation remains common to CPU RGBA and GPU NV12 output, with the original per-eye crop clamp and source/fence leases.

Color validation belongs to the existing native encoder/decoder tests. Synthetic bars exercise the actual PC encoders, their emitted metadata, and the Frame decoder; existing Vulkan fixtures separately check YCbCr conversion and sRGB reconstruction. GPU tests are explicitly requested and never inject synthetic media into a live streaming connection. Their result is specific to the tested GPU/driver and is not wearer acceptance.

Negotiated `frame_pose_time` sessions use fresh current-time Stage queries for head and both grips on each upload tick. The XR thread owns action/optics snapshots and handle lifetime; its private sampler serializes upload-thread locates against teardown. Frame SurfXR owns bounded per-session clock exchange; PC server_core validates sample time, epoch and sequence. OpenVR publishes the original poses/velocities with mapped sample age and leaves prediction to SteamVR. Legacy sessions retain client head prediction learned from query-to-display feedback and PC controller prediction. SurfXR Duration remains a ledger identity, not a PC-clock measurement. See [FRAME_POSE_TIME.md](FRAME_POSE_TIME.md) for byte layout, lifecycle and validation.

Windows `server_openvr` direct-mode capture retains the actual layer-zero submitted pose in timed mode, or the matched `PoseHistory` matrix for legacy sessions. `CEncoder` passes that target to `FrameRender`; every layer is rotated to the same orientation used by its video metadata. Timed capture removes the universe transform and freezes the source pose once per existing tracking identity before acquiring image ownership. Empty, missing, stale or duplicate timed identities cannot replace a previous source's metadata. Existing v21 video views carry this pose without changing GPU IPC, source timestamps, queue bounds or leases. This remains rotational reprojection without depth: translation differences and near-field parallax require separate measurement. The opt-in `--render-pose-probe` checks actual renderer/history behavior for both modes and a mismatched negative control; it is not headset acceptance.

Decoder allocations sampled by Vulkan remain immutable and retained until their GPU work completes. Upload completion alone does not release allocations still needed by reconstruction. Shutdown retires render work before decoder/device teardown; service shutdown waits for child completion. Audio and microphone capture have explicit bounded start/stop ownership.

Native Frame VR requires `frame_pose_time` plus `frame_clock_calibration`. `frame/surfxr/clock_fit.hpp` owns four-timestamp offset/rate interval fitting; `pose_clock.hpp` owns bounded requests, continuous clock-rate discipline and sample stamps. PC `frame_clock.rs` validates per-packet revision, uncertainty, rate and calibration age. Calibration failure is explicit; a calibrated session cannot switch to legacy prediction, arrival time or a fixed clock offset. No SteamVR display-latency actuator or expiry-to-baseline branch exists. See [FRAME_POSE_TIME.md](FRAME_POSE_TIME.md) for the negotiated v2 suffix, assumptions, limits and regression evidence.

New SurfXR images retain their actual source poses for runtime composition. Retained images use the enabled local rotational correction: `timewarp.cpp` and private `late_timewarp.hpp` query stereo views at the unchanged local display target after staging/prior GPU waits. Reconstruction samples immutable decoder pixels and submits the orientation represented by its output. Depth-dependent source eye positions/FOV remain unchanged; stereo validation, decoder leases, GPU fences and shutdown order retain their owners.

Boundary and IPD are read through the runtime bridge, independent of the media worker. A reference-space transition must not label a pose from a previous Stage epoch as current. Local system input capture must be explicitly selected and is released on teardown.

Headset battery percentage defaults to the local SteamVR HMD property, sampled by the existing runtime bridge and passed through `frame/app` to `frame/tracking`'s battery monitor. The runtime's display percentage can differ from raw Linux power-supply capacity. Runtime samples retain their original monotonic timestamp and expire after five seconds; unavailable/invalid/stale runtime samples fall back to the independently polled sysfs battery (30-second expiry). The local `SyncRawBattery` preference selects raw capacity only, without runtime substitution when raw data is unavailable. It is saved in input-preference format v5; v1-v4 files retain their settings and default to runtime display sync. Existing launcher acceptance serials apply to live edits. Dashboard reuses the battery monitor to display raw capacity even when streaming is idle. This uses a separate private bridge datagram and leaves SurfXR battery wire bytes unchanged. Battery uploads use their own freshness checks even when tracking poses are unavailable; PC forwards the received fraction unchanged to SteamVR.

## Build and installation

CMake uses `cmake/public_includes.cmake` for stable include roots. `scripts/build/project_manifest.py` owns native Frame input selection; it excludes the independently built Cargo tree. PC CMake resolves the companion headers from `pc/surfxr-server`. No sibling checkout is required. `runtime_sdk.cmake` resolves OpenVR from the included SDK on independent Linux builds, and OpenXR from the configured development headers and shared loader.

Native installation stages embedded launcher assets and binaries, verifies release hashes and installs the service at `%h/.local/share/surfxr-client/launcher/surfxr-client`. Source and installed paths remain distinct. Root scripts forward to the single orchestration owner. Build-only validation has no deployment side effects.

## Line-limit baseline

All maintained Frame/shared/PC extension code follows the 500-line limit. The imported ALVR workspace contains upstream files larger than 500 lines, including generated ABI headers, third-party libraries and existing Rust modules. Keeping the imported baseline intact makes upstream comparisons reliable; changes to these files require separate review.

The concrete exceptions are **only** the files listed in `UPSTREAM_LINE_BASELINE.json`. Each row records exact path, line count and SHA-256. Ownership is the SurfXR import under `pc/surfxr-server`, or the vendor import beneath it. `check_structure.py` accepts an exception only when its bytes still match that baseline; new or changed oversized files fail. Later edits must split the file by responsibility or explicitly document and review a replacement exception. Do not include functions as numbered fragments.

## Provenance

OpenVR SDK submodule revision: `0924064316de3effbcd1acf1e309182a2deb1c05`.
OpenVR is sourced from `https://github.com/ValveSoftware/openvr.git` (tag `v2.15.6`) at the gitlink above. The parent Git tree contains only `.gitmodules` and a mode-160000 entry, not the SDK files. Initialize with `git submodule update --init --recursive`; a plain source ZIP is insufficient. The SDK is external to the 500-line source-import baseline. Existing headers and libraries match the former import byte-for-byte, so this changes dependency ownership, not runtime ABI or behavior.

## Local Linux and cross compilation

`build_viewer.py --local` delegates execution to its private `build_local.py` module, retaining the authoritative source manifest and existing CTest suite. Reports distinguish native x86_64 from ARM64 ELF output and hash all required programs. ARM64 release packaging accepts only validated ARM64 output. The local path copies verified files directly without SSH. `cmake/toolchains/linux-arm64.cmake` uses Ubuntu multiarch libraries and QEMU for CPU tests; runtime rendering remains a separate acceptance step.

SurfXR owns the `surfxr-client` installation/configuration/state roots, `surfxr-client.service`, `surfxr-dashboard.service`, and `00_surfxr_exo_input` SteamVR driver identity. Other installation roots are not imported. Public `surfxr/*.hpp` include paths, C++ namespaces and PC service ABI are maintained together. These internal interfaces carry SurfXR and local application data only.

## Project naming

Project-owned C++ namespaces and public include paths use `surfxr`; compile-time options, macros and diagnostic environment variables use `SURFXR_`. Native PC executables are `surfxr-desktop.exe` and `surfxr-daemon.exe`; their companion DLL is `surfxr-desktop-module.dll`. Dashboard, service installation, DLL loading, Cargo staging and release manifests must change together. Native libraries and test targets also use the `surfxr-` prefix. Upstream SDK API spellings and binary dependencies remain unchanged.

SDK freshness is build metadata, never a runtime admission condition. The Frame launcher, installer and viewer must not reject installation, connection or desktop/VR switching solely because an SDK is old or its version/date differs from the headset OS. SDK/version comparisons and dependency preflight diagnostics are advisory; use actual public runtime capabilities and compatible ABI contracts. Release tooling owns delivering usable dependencies: an outdated build SDK must not be left as a user-facing reason that streaming cannot start. Resolve actual loader/ABI failures through a compatible build or properly packaged runtime dependencies, not cross-major library symlinks or a bypass that still crashes. Manifest integrity, executable architecture, protocol safety and real runtime failures remain independently enforced.

Release artifacts must not depend on a particular build SDK installation or on its private filesystem paths. Redistributable application libraries such as FFmpeg belong to the application payload, with compatible transitive dependencies, licenses and corresponding source/rebuild information where required. SDK freshness checks stay advisory. Platform-provided glibc, graphics drivers, Vulkan/OpenXR/OpenVR, desktop/audio services and their documented public ABI baseline remain system contracts, checked by actual availability/capabilities rather than SDK identity.

Frame media dependency preparation belongs to `scripts/build/frame_runtime.py`, called only by the existing local ARM64 target-SDK build owner. It builds pinned LGPL FFmpeg and BSD dav1d from verified source archives; dav1d is linked into the private FFmpeg shared libraries. Only libc/libm and other declared C runtime dependencies may remain external in that media dependency closure. The release manifest hashes `payload/build/runtime/lib` and `runtime/licenses`; the native installer copies them to application-owned `lib` and `licenses`. The viewer uses origin-relative library lookup, so its FFmpeg ABI comes from the release even when the headset provides a different FFmpeg major. No global library path, system package replacement or cross-major symlink is used.

All generated compilation output is under repository-root `build/`: native PC CMake uses `build/pc/native`, Cargo uses `build/cargo` and stages the streamer in `build/pc/surfxr_streamer_windows`. Local client configurations use `build/frame/<configuration>`, validation reports use the selected client directory or `build/reports`, and package staging uses `build/package`. Final distributables are written to `release/`. Downloaded source SDKs remain under their existing ignored dependency roots. Old output was relocated to `build/legacy` for reference; relocated CMake caches are not reused. These output locations keep new builds separate from an already running previous installation. A build does not update that installation or restart its services. Install the complete matching PC payload when upgrading, not one renamed executable in isolation.

Local preference writers emit `SURFXR_FRAME_` headers. The private `frame/preferences/preference_format.hpp` reader accepts the historical two-byte product tag with the same strict schema/version validation, so existing settings, image quality, input preferences and layouts survive an upgrade. Subsequent saves use the current header. Network bytes, GPU IPC layouts and configuration values are unchanged. The user-facing client remains SurfXR and retains its installation/service identities.

## SurfXR independent product boundary

SurfXR 1.0.0 is based on ALVR. PC crates, public native includes/namespaces, binaries, service/registry identities, package names and Frame installation roots use SurfXR/surfxr/SURFXR_. The original Android/OpenXR/mock clients, their graphics crate, ADB implementation, upstream release launcher and updater, unused C server API, and OpenVR samples/code generators/SDK source were removed. The bundled public SDK headers and required binary libraries remain with their licenses. Existing upstream-client session fields are inert compatibility data, hidden from the Dashboard; no removed client is built or installed.

Product version is separate from `WIRE_VERSION` and `protocol_id()`. Stream configuration serializes the original wire revision without changing the saved product session version. Fixed-size discovery marks, authentication domain separators and migration readers intentionally retain historical literal values; these are protocol/configuration contracts, not product identifiers or update sources. No new runtime adaptation was introduced; the existing bounded public-ABI forwarding remains governed by RUNTIME_ADAPTATION.md.

Dashboard Installation owns the Frame installer UI; `frame_installer.rs` validates arguments and invokes the existing packaged/`scripts/Install-Frame.ps1`. Plan runs without a console and keeps its output in the page. ## Streaming menu controls

`frame/ui` owns translated Capture 1..4 and keyboard attachment labels. Its topbar exposes Take Over using the existing system-input availability and explicit capture request, and Dashboard using a distinct semantic event; neither entry terminates streaming. `frame/app` wakes the installed Dashboard's existing private `overlay.sock` owner with a nonblocking show datagram. Missing/unsafe endpoints only report a diagnostic. No alternate launcher or process is created.

The UI's panel visibility records user capture intent. `frame/xr` maps panel source IDs to a persistent four-bit mask independently of render demand; `frame/app` shares it atomically with `frame/surfxr`. The authenticated capture request/ACK contract is owned by `shared/surfxr`; `pc/desktop` applies it on its video owner and drains the bounded sender before acknowledging. GPU/encoder owners are retained until normal teardown; see [PROTOCOL.md](PROTOCOL.md). This extension introduces no runtime-internal adaptation.

`frame/ui` owns the generic shortcut bar and local key recorder. Space/left-hand/right-hand attachment controls remain in the footer; the right-side bar shows three unnamed scan-code chords at a time. Pointer-over-bar stick input scrolls one slot, with per-hand 250 ms repeat and hysteresis; it never executes a shortcut. Arrows also scroll; trigger selects a visible chord. Add records a new chord, Edit then chord opens its recorder; Save, Cancel, Clear (new) and Delete (existing) have distinct outcomes. At most 24 chords of eight unique keys are accepted. Input/focus loss cancels recording. Settings replaces duplicate Keyboard/Close actions with Close Settings and moves Reset Position out of the keyboard toolbar into settings, without changing the independent view-recenter action.

`frame/preferences` input preferences v9 persists a bounded ordered shortcut list through its existing asynchronous atomic store. Defaults are Ctrl+Space, Ctrl+V/C/X/Z/A. v1–v7 use these defaults; v8 untouched Win+Space/Shift defaults migrate to the list, while customized v8 slots remain first and gain the remaining standard chords. Empty lists remain empty. `frame/app` accepts bounded ShortcutChanged insert/edit/delete events; list controls never send input. `shared/protocol/SessionInputQueue` retains atomic neutral/downs/reverse-ups/neutral admission and overflow all-up. PC ABI v2, authorization and physical scan-code events are unchanged. Candidate image streaming, tokens, negotiation, display and clicks are unchanged. No runtime-internal adaptation is introduced.

Reset confirmation is owned by `frame/ui`. Display confirmation is rendered inline in that display’s existing bottom control strip, beside Reset; it neither opens nor moves the keyboard/settings panel. The strip stays visible until resolution even after normal hover expiry; pointer input is reserved for its cancel/confirm controls. Only complete-layout confirmation uses the keyboard/settings modal surface. A display's local Reset requests only that panel's position, size and curvature reset; confirmation contains its display number and action buttons, with no explanatory scope text. Other panels, visibility, keyboard, preferences and connection are untouched. Complete layout reset is in the settings bottom action area, never in the header/shortcut bar. Its confirmation describes all display geometry/visibility and keyboard position/size/attachment; accepting restores the default space keyboard plus all display layouts, keeping shortcut, image and connection preferences. Cancel, focus/tracking loss, panel replacement and display unavailability dismiss without changing layout. Underlying controls and candidate interactions cannot receive modal clicks. State is persisted through existing layout export/store, without a new format, endpoint or runtime-internal adaptation.

Live VR bitrate updates carry the encoder bitrate snapshot into the existing bounded video queue. The socket owner updates an already enabled Frame UDP pacer before transmitting that packet, with the same twice-encoding-rate budget and an allowance for the daemon envelope. Changed rates discard old pacing debt; unchanged packets preserve the burst schedule. Encoder threads do not acquire the network writer lock; socket threads do not acquire settings locks. Unpaced/TCP transports retain their behavior. This fixes a stale startup-rate budget that can starve a raised bitrate into repeated queue overflow/IDR recovery. Queue bounds, wire bytes, picture metadata and decoder/GPU leases are unchanged.

Desktop candidate overlays are owned by the existing `pc/daemon/Keyboard` capture worker and `frame/surfxr` receiver, enabled only by the negotiated `frame_desktop_keyboard` extension and input permission. The worker retains one latest image for the control owner, at the existing 10 Hz capture cadence; it never waits on a network write. Desktop mode routes only token-bearing candidate clicks to this worker. Ordinary desktop pointer, key and release events retain the desktop module owner. Images are bounded by the existing 64 KiB codec, filtered by source generation and cleared when changing modes. The overlay can operate with every desktop capture disabled. VR keeps its existing video suffix. See [PROTOCOL.md](PROTOCOL.md). No runtime-internal adaptation is added.

Dashboard numeric controls keep slider/text-editor focus identities separate when combining layout responses. Enter and focus loss commit the edited value through the existing session writer; a label redraw alone is not acceptance. Unchanged focus transitions do not write settings or advance acceptance metadata.
