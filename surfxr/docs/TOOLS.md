Native `surfxr-client --deploy start` requires `mode` and `link` in its JSON request. It forwards the selected link as the connection service's optional `start.profile` and applies it before discovery/launch. An active session on another profile is rejected without changing its connection/configuration; no automatic link substitution occurs. Normal `start` requests without `profile` keep the saved selection. Release installation preserves saved profiles; an explicit start selects the requested one while preserving both endpoint records and remembered hosts.

Paths beginning with `scripts/` are relative to the repository root; other module paths are relative to `surfxr`. Use `--help` or PowerShell parameter help for current contracts. Offline tests must not contact an active server. Native loopback tests reserve their own endpoints; package/install tests use isolated staging and fake system commands.

Color checks reuse the native build: `surfxr-nvenc-color-test --gpu-test` exercises the production VR encoder, and `--software-test` exercises its optional GPL software alternative using offscreen D3D staging. Both write only synthetic fixtures under the configured native build directory. `surfxr-desktop --gpu-self-test` also checks production desktop encoding; `--color-output <directory>` optionally saves its synthetic fixture for Frame validation. Use a repository-root `build/` directory for these outputs. The existing Frame `surfxr-video-test` accepts `--color-bars on` with those 1024 x 256 fixtures, reporting independent RGB errors alongside raw/effective color metadata. CPU CTest includes `software-encoder-color`; hardware encoding and device decoding are separate explicit checks.

Transfer regression checks reuse `surfxr-nvenc-color-test --render-color-probe`: it loads the exact production FrameRender CSO blobs and uses the production input owner to check sRGB, UNORM and linear FP16 interpretation, overlay alpha, channel order, original-resource identity and unchanged sampling-view formats. Edge controls preserve the existing sampling domains rather than require a new filtering algorithm. Frame's existing `surfxr-foveation-gpu-test --linear-layout-check` covers matrix/range, packed-eye seams and poisoned padding. These commands fail on incorrect output and do not start SteamVR/OpenXR sessions or network streams. Identify software Vulkan separately from a physical GPU or headset run. The previously added `--color-filter-probe` was removed when the scope was corrected to color interpretation rather than resampling changes.

The imported PC FrameRender pixel shader uses the Windows SDK `fxc.exe`, entry `PS`, profile `ps_5_0`, optimization `/O3`, and source `pc/surfxr-server/surfxr/server_openvr/cpp/surfxr_server/shader/FrameRenderPS.hlsl`. Generate into root `build/pc/native/shaders/FrameRenderPS.cso`, copy it to the corresponding tracked `platform/win32/FrameRenderPS.cso` asset used by `graphics.rs`, then verify with the existing color test. The current regeneration used SDK 10.0.26100.0. No alternate shader compiler or runtime shader generator is needed.

Pose/overlay regression uses the same `surfxr-nvenc-color-test` target with `--render-pose-probe`. This explicitly runs offscreen D3D on the selected physical adapter, linking production `FrameRender`, its CSOs and `PoseHistory`. Synthetic scene/overlay layers test image-to-metadata rotation agreement for both eyes; the old layer-zero target is a failing negative control. No shader compilation, networking, desktop capture or SteamVR session is involved. Build with `cmake --build build/pc/native --config Release --target surfxr-nvenc-color-test --parallel 2`; put captured output under root `build/reports/`. Translation/depth correction and headset acceptance are outside this fixture.

Client display correction uses the existing offline CTest suite (`late-timewarp` for runtime-query/source-pose behavior) and the explicitly invoked `build/frame/linux-x64/surfxr-foveation-gpu-test --timewarp-check` for production Vulkan reconstruction, including gaze atlases. The latter is an offscreen GPU check; record whether the selected Vulkan device is software or hardware. No live OpenXR session or streaming endpoint is involved.

The Dashboard build script generates overlay bindings and its public interface identifier from the pinned OpenVR SDK submodule using the existing bindgen/libclang toolchain prepared by `scripts/Build-PC.ps1`. Runtime adaptation checks remain in existing CTest owners (`runtime-forwarding`, `openvr-boolean-input`, `system-input`); see [the adaptation policy](RUNTIME_ADAPTATION.md).

PC Dashboard Installation / Steam Frame client invokes the existing `scripts/Install-Frame.ps1` with `-Action install`, explicit SSH target, link and extracted release directory. `-Plan` previews without device changes and its captured output stays in the page. Dashboard installation additionally passes `-PairOnInstall` and a reserved `-DashboardResult` path through the root and launch entries; the existing release transport emits one SSH-verified identity receipt only after successful installation. The current Dashboard session owner saves trust and confirms it. The private flag requires release installation and cannot be combined with BuildOnly/removal; it does not start streaming. Original manual scripts remain supported.

PC builds bundle their matching entry and launch adapters in `frame-installer/`; update that directory together with Dashboard, including during a local deployment. `frame-client/` remains the separately selected and hash-verified ARM64 package. Dashboard Plan also passes `-PairOnInstall` so its command preview includes the identity query that execution will perform. The private `frame_release_commands.ps1` generator supplies both preview and execution: SSH/SCP argv, exact remote command strings and UTF-8 stdin. Fresh staging IDs differ per run; `${REMOTE_ROOT}` in previews denotes the validated absolute path returned by preparation. Native `--deploy install` remains the existing installation owner, not an invented shell script. Plan performs local manifest checks but no DNS, SSH/SCP or remote changes.

SurfXR default ports are isolated from ALVR; see [network endpoints and migration](NETWORK_PORTS.md). Both endpoints, firewall profiles and persisted-default migration must be maintained together.

Automatic pairing uses an explicit IPv4 SSH identity query (`-4`) against the authenticated target, matching PC admission. Other install/transfer calls keep their existing address-family selection. This avoids treating a Frame-local IPv6 interface scope as a Windows pairing address. The preview includes this exact option. Invalid identity still prevents trust; failure after native installation explicitly reports installation complete / automatic pairing failed, once.

The existing `surfxr-nvenc-color-test --bitrate-probe` explicitly runs the production HEVC/NVENC encoder on synthetic moving noise and a static image, without desktop capture, networking or live settings changes. It checks 100/200/300/400/100/300 Mbps reconfiguration with CBR, P1, low latency, spatial AQ, forced three-way split (where supported) and filler disabled. Measure encoded bytes after warmup at the configured 120 FPS; this is encoded-frame budget evidence, not a real-time transport throughput benchmark. The static control demonstrates that CBR without filler may use less than the target. Save output under root `build/reports/`.

The same target accepts `--quality-probe` to compare production HEVC P1/P3/P5 and single/quarter/full-resolution frame analysis at 200/300 Mbps. Identical synthetic 3840x2160 grayscale translation and changing-texture sequences are decoded with FFmpeg; output reports full-range luma PSNR, detail-region MSE, encoded-frame budget, and mean/p95 wall time around production Transmit. Spatial AQ is held constant: PSNR is a comparative error measure here, not a perceptual-quality verdict. No capture, network, extra encoder buffering or user-setting changes occur. Trials run unpaced and do not measure real-time transport or motion-to-photon latency. There is no portable preset-performance threshold; compare results on the target GPU and separately test headset responsiveness.

Dashboard removal uses the same verified release and SSH/native removal owner with `-Action uninstall`, keeping settings. The result adapter accepts uninstall without `-PairOnInstall`; installation retains its explicit pairing contract.
