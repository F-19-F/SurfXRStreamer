# Repository workflow

- Contributor entry: [CONTRIBUTING.md](CONTRIBUTING.md). Detailed workflows: [agent maintenance](surfxr/docs/AGENT_GUIDE.md), [feature development](surfxr/docs/DEVELOPMENT.md), [testing and acceptance](surfxr/docs/TESTING.md), and [user requirements/prompts](surfxr/docs/REQUESTS.md). Keep these guides aligned with actual code/tool contracts. Documentation-only changes need structure, link, command and diff checks, not unrelated runtime builds.

- This is the independent SurfXR PC + SurfXR client repository. SurfXR is based on ALVR and is the only client backend. Product releases start at 1.0.0; the default wire revision remains 21.0.0-dev14. Keep the PC and Frame implementations in the same repository and update both ends of an extension together.
- Read `surfxr/docs/ARCHITECTURE.md`, `TOOLS.md` and `PROTOCOL.md` before editing. State the owning module, responsibility and affected interfaces before work. Explain scope expansion.
- PC runtime code belongs in `surfxr/pc`, headset code in `surfxr/frame`, genuinely common code in `surfxr/shared`; repository tooling belongs in `scripts/`. Each subsystem owns its private headers. Stable public `surfxr/*.hpp` roots are declared by `cmake/public_includes.cmake`.
- Commit every coherent validated change. Do not stage unrelated changes, credentials, private captures, build directories, dependency caches or user settings. Report commit IDs.
- Every repair report must explain the observed failure, root cause and evidence, concrete repair mechanism, normal-use impact, validation and remaining limits. "Fixed" without this information is not a maintenance report.
- Do not cure an intermittent bug by noticeably degrading every normal interaction. Compare normal-path latency/responsiveness before and after; reject blanket waits, repeated reacquisition and broad lockouts when a targeted repair can preserve the common path.
- Minimize runtime gates. Do not add unnecessary or overly strict gates justified only by ideal conditions. For each maintained gate, identify the concrete failure it prevents, realistic jitter/loss/load behavior, cost to normal use and least disruptive recovery. Remove redundant gates; prefer rejecting a bad sample or continuing a stable state over aborting a healthy stream. Preserve authentication, bounds and resource-lifetime correctness. Keep the inventory in `surfxr/docs/GATE_REVIEW.md` current.
- New and maintained code must be at most 500 physical lines per file. Run `python scripts/build/check_structure.py`. Imported ALVR baseline exceptions are enumerated by path, line count and SHA-256 in `docs/UPSTREAM_LINE_BASELINE.json`; architecture explains their scope and ownership. OpenVR is an external pinned Git submodule and is excluded from this source-import baseline. Never silently extend the exception list. A changed oversized import must be split or have a concrete reviewed exception recorded.
- Do not fix runtime compatibility by hard-coding a product version/build, address/RVA, private object offset, private interface version, or captured instruction byte template. Prefer public APIs and capability queries. If runtime-internal adaptation is unavoidable, derive it dynamically from the running implementation, validate memory bounds and call semantics, and fail safely with a diagnostic when unproven. Every maintenance report must explicitly label such adaptation, explain why it is needed, what is parsed, validation/rejection behavior, tested evidence and remaining compatibility limits. ISA encodings, SDK-declared public ABI/protocol constants and reproducible dependency pins are contracts, not permission for version-specific runtime patches. See surfxr/docs/RUNTIME_ADAPTATION.md.
- Preserve SurfXR wire bytes, configuration formats, IPC acceptance serials, shutdown order, queue bounds, metadata/eye association, decoder leases and GPU source/fence lifetimes. Reserved local storage slots have no runtime controls.
- Reuse existing owners: `scripts/Build-PC.ps1`, SurfXR `cargo xtask`, `scripts/Start-Frame.ps1`, `scripts/launch/frame_remote.py`, native `frame/launcher` installation, `build_viewer.py` and `project_manifest.py`. Do not create alternate launchers, source manifests, shader compilers or timing collectors.
- All compiler outputs, Cargo caches, validation reports and packaging staging belong under repository-root `build/`. Use `build/pc/native`, `build/pc/surfxr_streamer_windows`, `build/cargo`, `build/frame/<configuration>` and `build/package`; final distributable archives/installers belong in `release/`. Do not add build directories inside source modules. Keep installed/running deployments separate from build output.
- Public PowerShell entries in `scripts/` forward explicitly bound parameters to `scripts/launch`; keep signatures synchronized. `-BuildOnly` must never install, pair, or start/stop services. Installed service ExecStart is `%h/.local/share/surfxr-client/launcher/surfxr-client`; validate staged installation imports/assets and this path.
- Generate shader arrays through `scripts/shaders/compile_*_shaders.py` and `embed_spirv.py`; verify with `--check`. Do not hand-edit SPIR-V.
- Use existing tests and isolated loopback endpoints. Reserve test endpoints first; never send synthetic packets to a real user's streaming service. Freeze source edits during final validation so recorded hashes identify the committed code.
- Distinguish source/build checks, CPU/offline tests, offscreen GPU checks, actual headset rendering, and wearer acceptance. Never claim the latter from a successful build.
- Prefer local Linux/WSL builds through `build_viewer.py --local`; do not compile on a headset unless explicitly requested. Follow `docs/WSL_BUILD.md`. Client runtime/service identities use `surfxr-*`; PC branding remains SurfXR.
- Imported PC dependencies and license notices stay with their owning source tree. Avoid broad unrelated formatting in imported code.
- Project-owned native names use `surfxr` / `SURFXR_`; keep public includes, namespaces, CMake targets, PC DLL/executable lookup, installer and packaging references synchronized. Preserve upstream API spellings. Read the architecture's naming and preference-migration contracts before changing these interfaces.
